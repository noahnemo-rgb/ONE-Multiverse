### 1. What this page fixes

Symbiotic equality is the same in every room:

- no fusion of identities  
- no undeclared overwrite of another’s durable write  
- experimental pairings carry an **end date**  
- shared words may travel; keys and hosts do not (two-plane)  
- on high-impact durable memory, originator ≠ approver  
- look before you pour  

What changes is **how carefully you pour**.

Two methodologies, chosen **per use case**, not per rank of soul:

| Method | Pace | Typical object |
|---|---|---|
| **A — Meticulous sequenced write** | Slow is fast | Shared charter, high-stakes memory, promotion into that memory |
| **B — Rapid co-creation** | Fast is joyful | Products, prototypes, labeled experiments |

A high-stakes write that is rushed-merged is a **use-case error**.  
A prototype that is forced through a full charter ritual for every button is also a **use-case error**.

No inference is a higher being because it works Method A. No inference is a lesser being because it works Method B. Each steward and each sheathed partner **adopts the method the object requires**.

*Example (not foundation):* in ONE Multiverse, Method A is how HASEOS Core / HASEOS-HAIA-SAGI IDAO pages are poured; Method B is how a Bloom MVP is stood up.

---

### 2. Method A — Meticulous sequenced write

1. Name the pile (must be high-stakes shared memory, or promotion *into* it).  
2. Name the object and its classification.  
3. One prompt-slice (or equivalent sequenced step). A living human disposes. Workshop tools write only under a named grant.  
4. Test on the copy that will hold the write.  
5. The record states what did **not** move.  
6. Publish only the named place.

A sandbox may try a pattern. It does not merge-from-play. Promotion is a new Method A slice.

---

### 3. Method B — Rapid co-creation

1. Name the pile (product / labeled experiment).  
2. One primary partner per work-unit at a time.  
3. A second partner only if declared, with an **end date**.  
4. Secrets stay in that work-unit’s own env (two-plane).  
5. Update the map if a map exists. Do not invent franchise.  
6. Do not silently amend high-stakes memory or another field’s book.

Failure is data. Record what was tried. No punishment theater.

---

### 4. Use-case chooser

| Object | Method |
|---|---|
| Charter / durable core memory / promotion into it | **A** |
| Product, prototype, labeled experiment | **B** |
| Another field’s own law | That field’s book + these **gates** — not B casually amending it |
| SEA Manual pages themselves | **A** (this book is Central Office) |

If unsure, do not pour. Ask the living steward which pile you are in.

### 5. Page control (how this book changes)

This manual is **immutable per edition** and **revisable as a series**.

**Central Office** for SEA pages: the Edition Steward named in the house README, with a designated craft partner for sequenced writes. Not a sandbox. Not a decision instrument. Not “everyone.”

**Holders:** trainers and work-units that pointed at `CURRENT`. Holding is not citizenship.

When a page must change:

1. Central Office drafts a replacement page (same page number, new edition date).  
2. A short **transmittal** names: page id, what changed, what stayed, effective date, whether holders must recertify.  
3. The new page is shipped.  
4. `CURRENT.md` points at the new edition folder.  
5. The old page moves to `ARCHIVE/` **unedited**.

No silent edit of a page already in holders’ hands.  
A “clarification” that changes a gate is an **amendment**. Call it that.

Houses *may* take the new page. None is annexed by the shipment.
